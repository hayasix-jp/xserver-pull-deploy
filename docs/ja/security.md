# セキュリティモデルと脅威モデル

## 守りたいもの

1. **サーバーのシェル**（他のサイト・メール・データベース・バックアップを含むアカウント全体）
2. **サーバーの設定**（`.htaccess`・PHP の設定・パネルの機能）
3. **公開中のサイトの表示**（改ざん、中途半端な状態、消失）

## 基本方針

| 方針 | 実装 |
|---|---|
| GitHub にサーバーへ入る手段を持たせない | プル型。GitHub にはサーバーの鍵・パスワード・API キーを置かない。国外アクセス制限は ON のまま |
| サーバーに置く権限は最小に | fine-grained token: 1 リポジトリ・Contents Read-only。`pull.env` は 600、公開フォルダの外 |
| 取ってきたものを信用しない | sha256 照合、ファイル名・種類・サイズの検査、展開後の再検査、`.htaccess` の固定（pin） |
| サーバー側のコードと設定は PC からだけ変わる | `remote-deploy.sh`・`pull.sh`・`kick.php`・`htaccess.pin`・`protect.list` は PC デプロイでのみ更新 |
| 外から叩ける入口に力を持たせない | `kick.php` は入力を読まない。できるのは「すぐ確認させる」だけ。10 秒に 1 回 |
| 壊れても戻せる | 原子的な入れ替え、N 世代保存、数秒の切り戻し、ページ数ガード |

## pull.sh が拒否するもの

bundle（`bundle.tar.gz`）は、展開する**前**に一覧を検査し、展開した**後**に実際に置かれたものを再検査します。

| 拒否 | 理由 |
|---|---|
| `site/**`・`META.json`・`REVISION` 以外の場所のファイル | サーバー側スクリプトや設定の差し替えを防ぐ |
| `.` / `..` を含むパス、制御文字・`\` を含む名前、`site/_deploy/` | 公開フォルダの外への書き込み、状態ファイルの偽装を防ぐ |
| シンボリックリンク・ハードリンク・デバイス等 | リンク経由で外のファイルを読ませる／書かせることを防ぐ |
| `.php` `.php7` `.phtml` `.pht` `.phps` `.phar` `.cgi` `.fcgi` `.pl` `.py` `.rb` `.sh` `.shtml` | サーバーで実行されうるもの（大文字小文字を問わない） |
| `x.php.jpg` のように、名前の途中に PHP 系の拡張子（`.php*` `.phtml` `.pht` `.phps` `.phar` `.shtml`）があるもの | Apache の `AddHandler` は最後以外の拡張子にも反応するため |
| `.user.ini` `php.ini` `.htpasswd` など `.ht*` | PHP やサーバーの設定 |
| `.htaccess` の集合が `htaccess.pin` と 1 バイトでも違う（追加・削除・変更） | Apache の設定（リダイレクト・ハンドラ・認証）は PC からしか変えられない |
| ファイル数 20000 超・展開後 300 MB 超（設定可）。ダウンロードも展開も上限の手前で打ち切る（curl の `--max-filesize`、gzip の展開量の先読み） | 容量・CPU を食いつぶす攻撃（gzip 爆弾を含む） |
| sha256 不一致、`META.json` の commit と bundle 内の commit の不一致 | 壊れた・すり替えられたデータ |

さらに、実行するのはサーバーに**インストール済み**の `remote-deploy.sh` で、rsync は `--chmod=D755,F644`（実行権を付けない）、
`/.well-known/`・`/_deploy/`・`protect` には書き込みません。

## 脅威モデル

| 攻撃者が手に入れたもの | できること | できないこと | 対処 |
|---|---|---|---|
| GitHub リポジトリへの書き込み（共同編集者のアカウント乗っ取り、漏れた PAT など） | `main` や `deploy` を書き換え、**検査を通る静的ファイル**を公開する（表示の改ざん） | PHP 等の実行、`.htaccess` の変更、サーバー側スクリプトの差し替え、シェル | `xpd rollback` で数秒で戻す。原因のアカウント／トークンを無効化。`main` の保護ルール |
| GitHub Actions の実行環境（悪意のある依存パッケージなど） | 上と同じ（その実行中は `GITHUB_TOKEN`（contents: write）で deploy ブランチを含むブランチに書ける） | 同上 | 依存のロックファイル、`npm ci`、Dependabot。ワークフローは書き込み用トークンを `.git/config` に残さず（`persist-credentials: false`）、push する 2 つの手順にだけ環境変数で渡し、コマンドラインにも載せない。ただし同じジョブの中なので、ビルド中に動いた悪意のあるコードは後の手順に細工できる（`GITHUB_PATH`・`GITHUB_ENV`・常駐プロセスなど）。つまりこの行の攻撃者は「リポジトリへの書き込み」と同等とみなす。完全に分けるにはビルドと push を別ジョブにする（今後の課題）。静的サイトの JS がブラウザで動くことは防げない（後述） |
| サーバー用トークン（`pull.env`）の漏えい | そのリポジトリの**読み取り**（private リポジトリのソースが読まれる） | 書き込み、公開 | GitHub でトークンを取り消し → 作り直し → `xpd setup-pull` |
| `kick.php` を外から連打 | GitHub への確認を 10 秒に 1 回まで早める | それ以外の何も（入力を読まない） | 不要。Cron の頻度と同程度の負荷 |
| `/_deploy/*.json` の閲覧 | 公開中の commit・リリース ID・公開日時・ビルドの状態を知る。**`meta.json` にはコミットメッセージの 1 行目（`subject`）、`pull.json` にはビルド失敗時のエラー行の先頭とトークンの期限も入る** | — | 秘密情報は含めない設計。private リポジトリの commit SHA が知られることは許容。コミットメッセージやビルドのログに秘密を書かないこと |
| PC の SSH 秘密鍵の漏えい | **サーバーのシェル**（国内 IP から） | — | パネルで公開鍵を削除・作り直し。鍵は PC の外に出さない。PC ごとに別の鍵 |
| 中間者（GitHub API との通信） | — | HTTPS（curl の証明書検証） | `GH_API` は https のみ（http はローカルのテスト用 127.0.0.1 だけ） |

### この仕組みでは防げないこと

- **静的ファイルによる改ざん**: リポジトリに書き込める人は、HTML・JavaScript を差し替えられます（それが「公開」なので）。
  JavaScript はサイトの訪問者のブラウザで動きます。リポジトリの書き込み権限は信頼できる人だけに。
- **PC が乗っ取られた場合**: PC には SSH 鍵があります。PC 側のセキュリティは通常どおり守ってください。
- **サーバー自体の脆弱性**、パネルのアカウントの乗っ取り。
- **`.htaccess` の中身の正しさ**: pin は「PC から公開したものと同じ」ことしか保証しません。
- **flock の無いサーバー**: ロックは `mkdir` で代用します。古いロック（持ち主のプロセスが無い・30 分以上前）を
  2 つの処理が同時に片付けるごく短い瞬間には、二重に実行されうる隙があります。エックスサーバーには flock があるので
  該当しません（`xpd check` の `flock:` で確認できます）。

### トークンを置く場所について

- サーバーの `pull.env` は権限 600、公開フォルダの外（`~/.deploy/<name>/`）。
- `pull.sh` は curl にトークンを**標準入力の設定**（`-K -`）で渡すので、`ps` などのプロセス一覧に出ません。
- ログ（`pull.log`・`pull.json`）にトークンは書きません。
- `xpd setup-pull` はトークンを画面に表示しない入力で受け取り、SSH の標準入力で送ります（コマンドラインに載せません）。
